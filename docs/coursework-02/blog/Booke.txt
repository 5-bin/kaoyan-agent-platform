## 一、从需求分析走向可交互、可开发的设计

我们的项目“408-Agent 智能备考平台”面向计算机考研学生，希望将刷题、错题复盘、学情分析、院校查询和资料整理连接起来。学生既可以直接使用页面功能，也可以带着当前题目、学习记录或笔记向领域智能体（Agent）提问。

第一次作业主要回答“用户需要什么”，这次作业进一步回答三个问题：用户怎样完成任务，系统内部怎样协作，以及数据怎样保存和关联。我们围绕两条主线组织设计：

- **学练闭环：**选择练习 → 提交作答 → 查看判分 → 错题复盘 → 学情分析 → 确认补强练习。
- **备考决策与整理：**完善报考条件 → 查询院校或获取推荐 → 查看依据 → 整理资料与个人笔记。

### 2.2 用户端与后台范围

原型按账号资源、学习闭环和后台管理划分，共提供 20 个独立 HTML 入口；墨刀内通过统一组件连续导航。部分入口表示同一业务的不同状态，例如答题前后、诊断中和批次结束后。

| 院校与资料 | 院校列表、院校详情、备考资料、个人笔记 | 查询招生信息，阅读资料，保存和回看笔记 |
| 管理后台 | 题目录入与审核、资料审核 | 单题录入、批量预览与送审、审核通过或退回 |

### 2.3 重点交互一：从错题进入上下文辅导

学生提交答案后，页面展示判分、标准答案和解析。对于答错的题目，可以从错题本进入“带上下文辅导”，继续询问“我的选项错在哪里”。助手接收题目与作答背景，围绕本题解释思路，减少用户重复复制题干和描述过程的操作。

这条路径将“答错了”进一步连接到“理解为什么错”。练习判分由业务服务完成，智能体负责解释和辅导；诊断模式则在批次结束后统一展示结果，避免提前揭示答案影响诊断过程。


![02_错题上下文辅导](https://img2024.cnblogs.com/blog/3849112/202611/3849112-20261107002849447-534743381.png)


### 2.4 重点交互二：学情分析连接补强练习

学生在学习统计页查看知识点表现后，可请求助手分析薄弱环节。助手将分析结果和可执行的补强练习建议一起展示，学生确认后再创建练习批次。

这条路径中，学习记录提供分析依据，智能体将结果转化为学习建议，业务系统负责创建和管理练习。学生可以直接从建议进入下一轮练习，形成“记录—分析—练习—再记录”的闭环。

### 2.5 重点交互三：笔记建议先预览，再保存新版本

学生先选定已保存的笔记，再请求助手整理内容或提出修改建议。原型展示建议预览，由用户决定是否接受；确认后保存为同一篇笔记的新版本，并可查看历史版本。

我们为这一流程设计了未保存离开提示和版本冲突反馈，使学生能够清楚区分当前正文、助手建议和已保存版本。


![03_笔记建议预览](https://img2024.cnblogs.com/blog/3849112/202611/3849112-20261107003758510-841098183.png)


### 2.6 重点交互四：后台录入、预览与审核

后台原型覆盖题目录入、批量数据预览、整批送审和审核处理。录入时展示必要字段与来源规则，批量操作先呈现预览；审核人员可以通过或退回，并填写相应意见。资料审核也设置确认与取消路径。


![04_后台批量送审](https://img2024.cnblogs.com/blog/3849112/202611/3849112-20261107003833755-135315698.png)


### 2.7 视觉规范与原型检查

界面采用蓝白配色、固定侧栏与卡片布局，筛选、按钮、表格和状态标签保持一致。对答题、生成中、停止、重试、空数据、未保存和审核等状态给出明确文字反馈，关键页面提供“页面规则”说明。

## 三、概要设计：从系统分层到对象协作

### 3.1 总体架构与功能模块

系统由 Vue 前端、Java 业务后端、Python Agent 服务和数据基础设施组成。前端统一访问 Java 服务；Java 管理业务数据和正式结果，Python 根据当前任务解析意图、调度领域专家和调用检索工具。


![05_系统总体架构](https://img2024.cnblogs.com/blog/3849112/202611/3849112-20261107003947751-431021098.png)


| 层次 | 技术与组件 | 主要职责 |
| :--- | :--- | :--- |
| 表现层 | Vue 3、TypeScript、Vite、Element Plus | 页面展示、表单交互、练习作答、助手流式回答、后台审核 |
| 业务服务层 | Java、Spring Boot、MyBatis-Plus | 认证、档案、题库、判分、学情数据、会话任务、院校目录、笔记与审核 |
| 智能体服务层 | Python、FastAPI、会话协调器、领域专家 | 意图解析、任务编排、知识检索、院校筛选、解释与建议生成 |
| 数据与资源层 | MySQL、Redis、Qdrant、OSS、版本化语料 | 业务持久化、令牌撤销与导出缓存、向量检索、头像文件与知识资料管理 |

这种分工使各部分有明确的职责：Java 处理判分、事务和记录保存，Python 处理领域任务与内容生成。Python 使用 Java 提供的个人数据快照以及独立知识资料完成请求，不直接连接业务 MySQL。

### 3.2 领域 Agent 怎样融入系统

在需求层面，我们围绕学情分析与院校推荐组织智能能力；在内部设计中，将任务细分为六类专家，由协调器按当前请求选择执行。

| 专家 | 主要任务 | 与软件功能的连接 |
| :--- | :--- | :--- |
| 知识专家 | 知识问答、错题上下文辅导 | 从题目、错题或助手页面进入，展示解释与相应依据 |
| 学情专家 | 解释学习表现、归纳薄弱环节 | 使用 Java 提供的学习画像与有效作答快照 |
| 院校专家 | 按报考条件筛选、排序和解释候选 | 连接院校推荐页面，展示候选及来源 |
| 练习专家 | 提出补强练习建议 | 用户确认后，由 Java 创建练习批次 |
| 笔记专家 | 生成整理或修改建议 | 在个人笔记中预览，确认后追加版本 |
| 学习计划专家 | 根据目标和学习表现安排复习 | 在助手中展示分天任务与复习建议 |

知识问答通过 RAG 从版本化资料中检索相关证据，再组织回答并附带来源。院校推荐先完成条件筛选和排序，再按需生成解释；单所院校的目录事实查询由 Java 的院校目录服务处理。两类入口分别服务“查某校信息”和“比较候选院校”的需求。

对于“分析我的薄弱点，并安排下一阶段复习”这样的复合请求，协调器按数据需求和步骤依赖安排专家协作。练习创建、笔记保存等操作以用户确认作为交互节点，最终由 Java 执行并保存。

### 3.6 时序图：说明助手请求与关键算法交互

助手请求采用“计划解析—读取数据—流式执行”的两段式调用。Java 先获取任务需要的专家与数据类别，再读取对应的个人数据快照，最后将计划和快照交给 Python 执行。结果持续推送到页面，并由 Java 保存为正式记录。


![10_助手主链时序图](https://img2024.cnblogs.com/blog/3849112/202611/3849112-20261107004058278-345977050.png)


关键算法在这条链路中的作用如下：

1. **意图解析与专家调度：**将用户问题转为结构化任务，依据步骤依赖选择专家。
2. **知识检索：**根据问题检索版本化语料，使用关键词或向量检索结果组织有来源的回答。
3. **院校筛选与排序：**先按年份、专业、学位类型、考试科目和地区等条件形成候选，再展示排序与可选解释。
4. **练习判分：**Java 根据题目版本快照和标准答案判分，将有效作答纳入学习统计，供后续分析使用。

完整设计还包含练习诊断判分、院校目录查询、院校推荐及取消处理等时序，见 [T05 Agent 与调用设计](https://github.com/fzu-404-team/kaoyan-agent-platform/blob/main/docs/coursework-02/system/T05_Agent与调用设计.md)。

## 四、数据库设计：支撑学习记录、领域任务与历史追踪

### 4.1 数据域与存储分工

数据库设计围绕 28 张表划分为七个业务域，并配套字段字典、实体映射及 SQL 结构索引。通过按域分层，先说明全局关系，再展开具体表和字段。

| 业务域 | 代表表 | 保存的内容 |
| :--- | :--- | :--- |
| 账号与授权 | `user`、`assistant_privacy` | 账号、备考档案、助手数据使用范围 |
| 题库与版本 | `question`、`question_version` | 题目内容、来源、审核状态及历史版本 |
| 练习与作答 | `practice_session`、`practice_record`、`user_question_mark` | 练习批次、作答判分、错题与收藏 |
| 学情与自动推荐 | `learning_profile`、`learning_profile_history`、`learning_event` | 当前画像、历史变化、重算事件和推荐设置 |
| 院校与招生 | `school`、`school_detail`、`school_admission_metric` | 院校、专业年份、招生指标与来源口径 |
| Agent 任务与会话 | `task`、`chat_conversation`、`chat_message`、`chat_generation` | 任务输入输出、会话消息、生成尝试与终态 |
| 资料与个人笔记 | `document`、`personal_document`、`personal_document_version` | 审核资料、个人笔记正文与版本历史 |

MySQL 保存业务事实；Redis 保存令牌撤销信息和导出缓存；Qdrant 保存独立的知识向量索引；OSS 保存头像文件。领域知识以版本化语料管理，检索证据保留来源和版本，便于将回答与具体资料对应起来。

### 4.2 ER 图：先看全局，再看学习主链

### 4.3 关系数据模型

下面列出核心关系模式的字段节选。`PK` 表示主键（Primary Key）；`UK` 表示唯一键（Unique Key）。省略号表示未在博客展开的字段，完整类型、默认值、索引和约束见数据字典。

```text
user(id [PK], username [UK], role, target_school, target_major, exam_year, ...)
question(id [PK], subject, difficulty, review_status, ...)
question_version(question_id + version [联合PK], ...)
practice_session(id [PK], user_id, kind, state, ...)
practice_record(id [PK], user_id, question_id, session_id, question_snapshot, ...)
user_question_mark(id [PK], user_id + question_id [联合UK], ...)
school(id [PK], ...)
school_detail(id [PK], school_id, ...)
school_admission_metric(school_detail_id + metric_type [联合PK], status, ...)
task(id [PK], user_id, task_type, status, input_payload, result_payload, release_id, ...)
chat_conversation(id [PK], user_id, ...)
chat_message(id [PK], conversation_id, ...)
chat_generation(task_id [PK], message_id, attempt_no, status, ...)
personal_document(id [PK], user_id, ...)
personal_document_version(document_id + version [联合PK], ...)
```

主要联系包括用户与任务的一对多、院校与专业年份的一对多、会话与消息的一对多、笔记与版本的一对多，以及用户和题目通过错题收藏记录建立的多对多关系。题目版本和作答快照使历史作答能够按当时的题目内容回顾。

### 4.4 对象与库表映射

系统同时使用 MyBatis-Plus 的 ORM 映射和基于 JDBC 的直接 SQL 访问。已有 10 张表具有实体与 Mapper；会话、个人笔记及学习闭环等新增表通过相应服务直接访问。

| 对象或服务 | 对应表 | 映射方式与用途 |
| :--- | :--- | :--- |
| `User` / `UserMapper` | `user` | 实体映射，管理账号与备考档案 |
| `Question` / `QuestionMapper` | `question` | 实体映射，管理题目与审核信息 |
| `PracticeRecord` / `PracticeRecordMapper` | `practice_record` | 实体映射，保存作答与判分记录 |
| `UserQuestionMark` / `UserQuestionMarkMapper` | `user_question_mark` | 实体映射，管理错题和收藏 |
| `Task` / `TaskMapper` | `task` | 实体映射，保存任务及结构化输入输出 |
| `School`、`SchoolDetail` 及其 Mapper | `school`、`school_detail` | 实体映射，管理院校目录 |
| `ChatRepository` | `chat_conversation`、`chat_message`、`chat_generation` 等 | 直接 SQL，管理会话与生成记录 |
| `ManagedPracticeService` | `practice_session`、`practice_session_item`、`question_version` 等 | 直接 SQL，管理受管练习与题目版本 |
| `PersonalDocumentService` | `personal_document`、`personal_document_version` | 直接 SQL，管理个人笔记与历史 |

例如 Java 属性 `userId` 对应数据库列 `user_id`，`Task` 的输入输出对象对应结构化数据列。完整逐字段映射见 [T07 实体表映射](https://github.com/fzu-404-team/kaoyan-agent-platform/blob/main/docs/coursework-02/database/T07_实体表映射.md)，字段定义见 [T07 数据字典](https://github.com/fzu-404-team/kaoyan-agent-platform/blob/main/docs/coursework-02/database/T07_数据字典.md)。

### 4.5 领域知识、用户交互与任务结果怎样管理

- **领域知识：**语料按版本发布，保留来源定位；知识检索使用独立索引，回答携带本轮检索来源。
- **用户交互：**会话、消息和生成尝试分别保存，能够区分连续对话、重试和最终结果。
- **任务执行：**`task` 保存任务类型、输入、结果和状态；建议操作通过业务记录管理，确认后执行。
- **学习证据：**作答保存题目快照与判分状态，学习画像保存当前值和历史变化，使分析能够关联到有效作答。
- **个人笔记：**每次保存追加历史版本，助手建议确认后进入同一套版本管理流程。
- **院校信息：**专业年份与指标状态分开记录，展示时保留信息来源、统计口径与更新状态。

完整结构和存储策略见[数据库设计说明书](https://github.com/fzu-404-team/kaoyan-agent-platform/blob/main/docs/coursework-02/database/408小组_数据库设计说明书.md)。
